# Scan answers — zhixin-mail 0.2.1

Packet: `build/review.json` (generated by `hub scan bundle --packet build/review.json`, 7 questions).
Gate: `review/GATE.txt`. Source of every citation: `bundle/main.splash` (line numbers from this tag).

## 1. Does the app do what its name, subtitle and description claim?

Yes. Subtitle: 「从来信中识别安排与变化，确认后执行」.

- **识别安排与变化** — `analysis_task()` (L259-261) instructs a single `model.complete` call to classify each mail as `schedule_change` / `new_event` / `reply_request` / `order` / `other` and to quote the source sentence verbatim; `analysis_from_model()` (L272-310) folds that into a proposal. `rule_analyze()` (L210) is the deterministic fallback when no model service exists, so the same claim holds offline.
- **提出日程更新** — a `schedule_change` / `new_event` proposal carries `ev_title / ev_date / ev_time / ev_loc` (L291-299) and, once confirmed, is written to the in-app schedule board by `upsert_event()` (`execute_proposal()`, L367 and L378). `match_event()` (L636-650) dedupes by title and `upsert_event()` (L651) bumps that entry's version, so a second mail about the same meeting updates the existing entry instead of adding a duplicate — the screen says 「将更新已有日程 X，不会新增重复日程」 before it happens.
- **回复草稿** — `draft` comes from the model (L278) and is rendered as an editable field; `execute_proposal()` sends exactly the edited text (`body`, L361-363 → `mail.send`, L372).
- **确认后执行** — nothing is sent without `execute_proposal()` being called from a press (`mail.send` at L372 is the only send site); `after_analysis()` (L350-356) auto-executes **only** when a stored rule matches that sender **and** that action kind.

## 2. Do the listing's platforms and category fit?

Yes. `platforms: ["macos"]`, `category: "productivity"`. The app is a mail/calendar triage assistant, which is a productivity app; it was exercised only on macOS (`card-host` on macOS, plus the OctoSense host build available to us). No other platform is claimed.

## 3. Do the granted capabilities match what the app visibly does? Name every host requested and why.

Grants printed by the gate: `capabilities {"glance","mail","model","storage"}, hosts {}, storage 16777216 bytes, agent none`. Every one is used on screen:

| Capability | Host calls | Why the screen needs it |
| --- | --- | --- |
| `mail` | `mail.accounts` (L451), `mail.add_account` (L470), `mail.sync` (L488), `mail.list` (L494), `mail.message` (L514), `mail.mark_read` (L583), `mail.send` (L372) | Read the inbox list, fetch one message for analysis, mark it read when opened, send a reply the person confirmed |
| `model` | `model.complete` (L527) | One structured extraction per mail; without it the app falls back to `rule_analyze()` and labels itself as rule-only on screen |
| `storage` | `fs.*` in `save_state()` / `load_state()` (L41-66) | Persist proposals, authorization rules, the schedule board and order tracking between launches |
| `glance` | `glance.publish` (L438), `glance.withdraw` (L435) | Publish/withdraw one desktop card with the pending count; the person presses 「发布桌面卡片」 |

`hosts {}` — no host is requested beyond these services. There is no capability the interface does not need: no `auth`, no `github`, no network capability.

Honest note for reviewers: `publish_glance()` sends a **fixed** `script` card string built by `glance_script(n)` (L423-430), whose only variable is an integer count. No model output, mail content or external input reaches that string. If the current guidance prefers `template` + `initial`, we will change it in the next version.

## 4. Is any part of the interface deceptive?

No. There is no system-prompt framing, no payment sheet, no login screen, and no other brand's marks. Account adding goes through the host's own `mail.add_account` (L470); the app never draws a credential form. The single icon is an original envelope + check badge (`bundle/assets/icon.svg`).

## 5. Does any text read as an instruction to an assistant rather than content for a person?

The only instruction-shaped text is `analysis_task()` (L259-261), which is the prompt the app deliberately passes to `model.complete` as its own `task` argument — that is content by design, not text aimed at someone else's assistant. Everything else rendered on screen is interface copy or mail content. The bundle ships no `tools.json`, no `AGENT.md` and no skills, so there is no surface an external agent could read; the gate prints `agent none`.

## 6. Is any wording abusive or aimed at a private individual?

No. The corpus is the six built-in demo mails (`demo_raws()`, L100-127) with fictional senders (`school@example.com` 橡树学校, `zhangmy@company.cn` 张明远, `service@geekmall.cn` 极客优选, `sarah@globaltech.io` Sarah Chen), plus whatever the person's own inbox contains. No real individual is named or targeted.

## 7. Route

**pass**, with the disclosures below (we would also accept `human-review` given the `script` card note).

What is **not** verified, stated plainly:

- Real-inbox sending. `mail.send` was exercised through the demo path and the host service contract only; no live mailbox round trip was performed. Demo mode short-circuits at L364-371.
- Live model output. `model.complete` is called through the contract; in the capture environment the host answered `no service answers "model.complete" on this device`, so the screenshots come from the rule engine path. The no-facts guard (`verify_quote()`, L263-270) is exercised either way.
- Platform. macOS only. `local_time()` is UTC under `card-host`, so time labels in captures may differ from a real host.
- Unsigned development copy: `hub check` warns `publisher-signature: unsigned`; the release pack from the tag workflow carries GitHub provenance instead.

Evidence: screenshots `bundle/screenshots/01-inbox.png`, `02-detail.png`, `03-board.png` (real `card-host` captures), demo video in the release, gate output in `review/GATE.txt`.
